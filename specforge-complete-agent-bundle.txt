# AGENTS.md — Persistent Repository Context & Agent Contract

## Product
Multi-tenant B2B financial workflow and spend management SaaS application used by finance managers and department leads.

## Stack
TypeScript 5.7, Next.js 15 (App Router), React 19, Tailwind CSS v4, PostgreSQL 16, Prisma ORM, TanStack Query v5, Zustand, Zod, Vitest, React Testing Library, Mock Service Worker (MSW), Playwright.

## Repository Structure
```text
src/app/ -> Synchronous route shells, layouts, and <Suspense> boundaries
src/features/<domain>/ -> Domain Server Components, leaf Client Components, and Server Actions
src/services/ -> Pure business logic and data orchestration
src/lib/ -> Shared infrastructure, auth session helpers, and DB client
src/types/ -> Shared TypeScript interfaces and domain DTOs
```

## Commands
```bash
Install: pnpm install
Dev Server: pnpm dev
Typecheck: pnpm typecheck
Lint: pnpm lint
Unit/Integration Tests: pnpm test
Single File Test: pnpm vitest run <path/to/file.test.tsx>
E2E Tests: pnpm test:e2e
Production Build: pnpm build
```

## Architecture
- Keep route files (app/**/page.tsx) synchronous composition shells; never run inline DB/API queries in page.tsx.
- Feature components default to async Server Components; place 'use client' strictly on interactive leaf components.
- Page owns <Suspense>, Feature file exports matching *Skeleton at the bottom of the file.
- Keep server data in Server Components or TanStack Query v5 cache; never copy server data into global Zustand stores or useEffect state.

## Coding Conventions
- Prefer named exports for all components and services.
- Use composition (children and React.ReactNode slots) instead of boolean layout props (e.g., avoid hasHeader, showFooter).
- Use stable entity IDs (item.id) for React list keys; never use array index keys.
- Calculate derived state inline during render; never compute derived state inside useEffect.

## Testing
- Enforce Red-Green-Refactor TDD for every vertical slice.
- Query DOM elements strictly via React Testing Library accessibility hierarchy: getByRole -> getByLabelText -> getByText.
- Mock network boundaries with MSW; never mock internal custom hooks or use UI snapshot tests.

## Security
- Enforce server-side workspace and resource ownership checks inside every Server Action and API route.
- Treat client inputs (roles, prices, tenant IDs, user IDs) as untrusted; validate all external inputs with Zod at system boundaries.
- Never log raw JWTs, API keys, or PII in server or client logs.

## Database
- Prohibit destructive database migrations (DROP TABLE, DROP COLUMN) without explicit human approval.
- Require a non-blocking backfill migration plan whenever adding required columns to populated tables.
- Never edit already-applied migration files under prisma/migrations/.

## Generated Files
Never manually edit files in:
- src/generated/
- prisma/generated/
- openapi/generated/
- pnpm-lock.yaml
Regenerate types via: pnpm db:generate && pnpm openapi:codegen

EOF_AGENTS

# ARCHITECTURE-BOUNDARIES — Architectural & Security Invariants

## Mandatory Boundary Rules
1. Import invoke strictly from '@tauri-apps/api/core' (NEVER deprecated v1 '@tauri-apps/api/tauri').
2. Define Rust commands with #[tauri::command] returning Result<OutputDto, String> and manage shared state via tauri::State<'_, Mutex<AppState>>.
3. Register every command inside tauri::generate_handler![...] in src-tauri/src/lib.rs.

## Runtime & Security Enforcement
1. Canonicalize and validate all incoming file paths in Rust to prevent path traversal (../../../etc/passwd) outside allowed directories.
2. Declare explicit, least-privilege permissions in src-tauri/capabilities/default.json (never allow-all scopes).
3. Preserve tauri.conf.json build chain and add matching IPC mocks in src/__mocks__/ for Vitest.

## Do-Not-Edit Paths
Do NOT manually edit src/generated/, prisma/generated/, openapi/generated/, or pnpm-lock.yaml.

# Feature Specification (specs/001-feature/spec.md)
> **Zone A — Product Intent ("What & Why")**: Deliberately free of implementation stack bias.

## 1. Plain-Language Summary & User Intent
Build a team invoice approval workflow where workspace managers can filter pending invoices, preview line items, and approve or reject invoices with optimistic UI feedback and role-based audit logging.

## 2. Target User Persona


## 3. Observable Acceptance Criteria (EARS Notation)
1. **WHEN** a non-admin workspace member attempts to approve or reject an invoice, **THE SYSTEM SHALL** deny the mutation at the Server Action boundary, log an unauthorized audit event, and return a typed FORBIDDEN error union.
2. **WHEN** a workspace manager clicks Reject without providing a rejection note of at least 10 characters, **THE SYSTEM SHALL** prevent submission and display an accessible inline validation message linked via aria-describedby.
3. **WHEN** an invoice approval request succeeds or fails over the network, **THE SYSTEM SHALL** immediately transition the UI via useOptimistic and automatically roll back to PENDING with a retry toast if the server returns an error.

## 4. Required User Experience States
  - **LOADING**: Render <InvoiceListSkeleton /> with matching card height inside page.tsx <Suspense> boundary.
  - **EMPTY**: Render accessible empty state with "Clear Filters" action when no invoices match the URL status query.
  - **ERROR**: Render ErrorBoundary fallback card with a retry callback and correlation ID.
  - **OFFLINE**: Disable mutation buttons with tooltip indicating offline network status.
  - **DISABLED**: Disable Approve/Reject controls when user role is Viewer or invoice is already locked.
  - **SUCCESS**: Optimistically update badge to Approved/Rejected and persist audit log timestamp.

> **Zone A — Product Intent ("What & Why")**: Deliberately free of implementation stack bias.

## 1. Plain-Language Summary & User Intent
Build a team invoice approval workflow where workspace managers can filter pending invoices, preview line items, and approve or reject invoices with optimistic UI feedback and role-based audit logging.

## 2. Target User Persona


## 3. Observable Acceptance Criteria (EARS Notation)
1. **WHEN** a non-admin workspace member attempts to approve or reject an invoice, **THE SYSTEM SHALL** deny the mutation at the Server Action boundary, log an unauthorized audit event, and return a typed FORBIDDEN error union.
2. **WHEN** a workspace manager clicks Reject without providing a rejection note of at least 10 characters, **THE SYSTEM SHALL** prevent submission and display an accessible inline validation message linked via aria-describedby.
3. **WHEN** an invoice approval request succeeds or fails over the network, **THE SYSTEM SHALL** immediately transition the UI via useOptimistic and automatically roll back to PENDING with a retry toast if the server returns an error.

## 4. Required User Experience States
  - **LOADING**: Render <InvoiceListSkeleton /> with matching card height inside page.tsx <Suspense> boundary.
  - **EMPTY**: Render accessible empty state with "Clear Filters" action when no invoices match the URL status query.
  - **ERROR**: Render ErrorBoundary fallback card with a retry callback and correlation ID.
  - **OFFLINE**: Disable mutation buttons with tooltip indicating offline network status.
